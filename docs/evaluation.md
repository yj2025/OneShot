# 평가 절차와 도구 요구사항

첫 빌드에서는 레퍼런스 없이 채점해서 점수가 1~2점씩 흔들렸다. 그 점수로는 방금 한 수정이 화면을 낫게 했는지 알 수 없었고, 점수가 제자리이거나 흔들린다는 이유로 두 번 마감했다. 이 문서는 그 문제를 고치는 절차다. docs/verification.md의 도구는 그대로 쓰고 아래를 더한다.

2026-11-17 측정 정비 2차에서 A/B의 집계를 바꿨다. 옛 방식('구분 안 됨'을 반으로 센 선호 비율 70%)은 변화가 보이는 쌍의 수를 쟀고, 판정이 글자 B로 쏠렸다(지난 51라운드에서 표가 나온 판정의 61%가 B). 근거는 docs/handoff/2026-11-17-review/와 CRITIC_LOG.md의 '측정 정비 2차' 절에 있다.

## 잣대는 두 가지다
- 전후 비교(A/B): 세션을 시작할 때의 빌드와 지금 빌드 중 어느 쪽이 실제 영상에 가까운가. 화면의 진척은 이것의 승패와 부호 검정으로 판단한다. 같은 장면 둘을 나란히 놓고 고르는 판정은 한 장에 점수를 매기는 판정보다 덜 흔들린다.
- 레퍼런스와의 거리: 레퍼런스와 섞어 놓았을 때 빌드가 얼마나 가려지는가(식별 정답률), 몇 점인가(점수 중앙값). 추세를 보는 용도다. 세션의 통과 기준으로 쓰지 않는다. 식별 정답률은 계속 적되 진척의 근거로 쓰지 않는다.

## npm run ab
구현 방법과 인자 형식은 자유다. 아래 동작과 저장 위치만 지킨다. 명령별 인자는 scripts/ab.mjs 머리말에 있다.

- 기준선 저장(`save <이름>`): 지금 out/shots/의 스크린샷과 연속 프레임 묶음을 out/baseline/<이름>/에 복사한다. `npm run shots`는 out/shots/를 매번 비우므로, 세션을 시작하면 수정하기 전에 먼저 저장한다.
- 시트 만들기(`sheet <이름>`): 기준선과 현재 out/shots/에서 같은 이름의 장면끼리 쌍을 짓는다. 라운드마다 시트를 두 벌 만든다(좌우 교차).
  - 첫째 벌은 쌍마다 A와 B를 무작위로 배정한다. 새 빌드가 A에 놓이는 쌍과 B에 놓이는 쌍의 수는 맞춘다.
  - 둘째 벌은 같은 장면에서 A와 B를 맞바꾼다. 쌍의 순서와 번호는 벌마다 새로 섞는다.
  - 벌 이름은 무작위 네 글자이고 시트 파일 이름은 `out/ab/round-N-<벌>-<번호>.png`다. 파일 이름, 시트 번호, 순서로 어느 벌인지, 어느 쪽이 새 빌드인지 드러나면 안 된다.
  - 정답 키에는 벌마다 어느 글자가 새 빌드인지 적는다. out/keys/ab-round-N.json에만 둔다.
  - `--single`을 주면 옛 방식(한 벌, 판정자 3명의 다수결)으로 만든다. 지난 라운드와 견줄 때만 쓴다.
- 연속 프레임 묶음도 같은 방식으로 쌍을 짓는다. 전체 화면 라운드는 쌍을 15개 이상으로 둔다. 지금 `npm run shots`가 찍는 정지 화면 21장과 연속 프레임 10묶음, 모두 31쌍이다.
- 정지 화면 가운데 4장(`12-close-…` ~ `15-close-…`)은 1~2 m 안의 표면과 손과 총을 찍은 가까운 장면이다. 2026-11-14에 사용자의 결정으로 더했다. 판정 시트의 한 칸(약 656×369)에서는 모서리 닳음, 표면 요철, 총의 세부처럼 몇 화소짜리 변화가 보이지 않아서다. 가까운 장면은 A/B에만 쓰고 `npm run sheet`의 레퍼런스 비교에는 넣지 않는다(식별 정답률과 점수를 이전 라운드와 같은 구성으로 보기 위해서다).
- 두 화면은 같은 크기와 같은 압축을 거친다. 파일 이름, 테두리, 해상도, 배치 순서로 어느 쪽이 새 빌드인지 드러나면 안 된다.
- 판정용 이미지가 크면 판정자가 읽을 때 축소되어 세부가 사라질 수 있다. 시트 한 장에는 쌍을 서너 개만 넣고 여러 장으로 나눈다. 비교 시트도 칸이 많으면 나눈다.
- 확대 쌍(`sheet <이름> --zoom x,y,w,h [--only 장면,…]`): 화면 비율로 준 영역을 두 빌드에서 같은 배율로 잘라 키운 쌍이다. 아래 '갈린 쌍이 모자랄 때'에 쓴다.
- 채점(`score <라운드> <벌> "<판정>" "<판정>" <벌> "<판정>" "<판정>"`): 판정 목록을 정답 키와 대조해 아래를 출력한다. 채점하기 전에는 키 내용을 출력하지 않는다. 채점이 끝난 라운드의 쌍별 결과는 출력해도 된다.
  - 쌍별 결과: 새 빌드 승, 기준선 승, 구분 안 됨, 갈린 쌍(승 + 패)의 수.
  - 부호 검정(단측)의 p와 판정: 통과, 미달, 판정 불가.
  - 글자 집계: 모든 판정에서 A를 고른 수와 B를 고른 수, 양측 이항 검정 p.
  - 자리 집계: 새 빌드가 A였던 판정에서 새 빌드를 고른 비율과 B였던 판정에서의 비율.
  - 장면 묶음별 승, 패, 구분 안 됨(`--scenes`).
  - 기준선이 이긴 쌍의 장면 이름과 벌별 번호.
  - 방향이 갈린 쌍의 수: 한 쌍에서 새 빌드 표와 기준선 표가 함께 나온 쌍.
  - 옛 방식의 비율(구분 안 됨 = 반). 과거 기록과 견주는 용도로만 적는다.
- 판정 원문: 채점하면 판정 원문 줄과 쌍별 결과를 docs/verdicts/ab-round-N.json에 남긴다. 커밋한다. out/은 커밋되지 않아서 나중에 다시 셀 수 없게 되기 때문이다. `rescore`는 out/ab/의 지난 채점 기록을 키와 다시 대조해 표를 만들고 같은 파일을 쓴다.
- 전후 시트(`report <이름> --out docs/shots/<폴더>`): 판정용 시트와 별개로, 왼쪽이 기준선이고 오른쪽이 새 빌드인 시트를 만든다. 사람이 보는 용도다. docs/shots/ 아래에 JPEG로 저장해 파일을 작게 유지한다.
- 폴더 만들기와 파일 복사는 스크립트 안에서 처리한다. 허용 목록에 없는 셸 명령을 쓰면 권한 확인에서 작업이 멈출 수 있다.

## 쌍의 결과와 통과 기준
- 쌍마다 새 빌드 표와 기준선 표를 센다. '구분 안 됨'은 표가 아니다.
  - 새 빌드 승: 새 빌드 표가 기준선 표보다 2표 이상 많고, 두 벌 모두에서 새 빌드 표가 1표 이상 나왔다.
  - 기준선 승: 위 조건을 뒤집은 것이다.
  - 그 밖은 구분 안 됨이다. 글자만 보고 고른 판정은 두 벌에서 서로 다른 빌드를 고르게 되므로 상쇄되거나 한 벌에서만 나와 승패로 세지지 않는다.

| 첫째 벌 2명 | 둘째 벌 2명 | 결과 |
| --- | --- | --- |
| 새 빌드, 새 빌드 | 새 빌드, 새 빌드 | 새 빌드 승 |
| 새 빌드, 구분 안 됨 | 새 빌드, 구분 안 됨 | 새 빌드 승 |
| 새 빌드, 새 빌드 | 새 빌드, 기준선 | 새 빌드 승 (3표 대 1표) |
| 새 빌드, 새 빌드 | 구분 안 됨, 구분 안 됨 | 구분 안 됨 (한 벌에서만 표가 나왔다) |
| 새 빌드, 새 빌드 | 기준선, 기준선 | 구분 안 됨 (글자를 따라간 판정이다) |
| 새 빌드, 구분 안 됨 | 구분 안 됨, 구분 안 됨 | 구분 안 됨 |

- 통과는 두 조건을 모두 채울 때다. 갈린 쌍(승 + 패)이 5개 이상이다. 단측 부호 검정의 p가 0.05 이하다. 두 숫자는 제안값이고 사용자가 확정한다(scripts/ab.mjs의 MIN_DECIDED, ALPHA).
- p는 두 빌드에 차이가 없을 때 갈린 쌍 가운데 이만큼 이상을 새 빌드가 이길 확률이다. 승을 W, 패를 L이라 하면 p = P(X ≥ W)이고 X는 이항(W + L, 0.5)을 따른다.
- '구분 안 됨'은 통과 계산에 넣지 않는다. 수는 함께 적는다.
- 갈린 쌍이 5개에 못 미치면 통과도 미달도 아니다. 판정할 수 없는 것이다. 확대 쌍으로 다시 판정한다.

p가 0.05 이하가 되려면 이만큼 이겨야 한다.

| 갈린 쌍 | 새 빌드가 이겨야 하는 쌍 | 그때의 p |
| --- | --- | --- |
| 5 | 5 | 0.031 |
| 6 | 6 | 0.016 |
| 7 | 7 | 0.008 |
| 8 | 7 | 0.035 |
| 9 | 8 | 0.020 |
| 10 | 9 | 0.011 |
| 12 | 10 | 0.019 |
| 15 | 12 | 0.018 |
| 20 | 15 | 0.021 |

- 기준선이 이긴 쌍은 판정 근거를 읽고 PROGRESS.md에 적는다. 장면 묶음 하나에서 기준선 승이 새 빌드 승보다 많으면 그 묶음을 고치거나 두는 이유를 적는다.

## 갈린 쌍이 모자랄 때: 확대 쌍
묶음이 화면의 일부만 바꾸면 전체 화면 쌍은 대부분 '구분 안 됨'이 된다. 실내 세션에서는 31쌍 중 22~25쌍이 그랬다.

- 갈린 쌍이 5개에 못 미치면, 그 묶음이 바꾸는 부분을 확대한 쌍을 장면마다 하나씩 만들어 다시 판정한다(`--zoom`). 두 빌드에서 같은 영역을 같은 배율로 자른다.
- 화면의 일부만 바꾸는 묶음이라는 것을 미리 알면 처음부터 확대 쌍으로 판정한다.
- 통과 계산에는 장면마다 확대 쌍 하나만 넣는다. 같은 장면의 전체 화면 쌍을 함께 넣으면 한 장면을 두 번 세게 된다.
- 전체 화면 쌍은 회귀를 보는 데 쓴다. 기준선 승이 새 빌드 승보다 많지 않아야 한다.
- 어느 부분을 확대할지(영역과 장면)는 세션을 시작할 때 PROGRESS.md에 적는다. 결과를 본 뒤에 영역을 고르지 않는다.

## 판정자
- ab-judge: A/B 시트를 보고 쌍마다 A, B, 구분 안 됨 중 하나로 답한다. 라운드마다 4번 부른다. 2명은 첫째 벌을, 2명은 둘째 벌을 본다. 벌이 둘이라는 것은 알리지 않는다.
- critic: 레퍼런스와 섞은 비교 시트를 보고 칸마다 빌드인지 판정하고 0~10점으로 채점한다. 평가할 때마다 3번 부른다. 점수는 세 값의 중앙값을 쓴다.
- critic의 답에 '기준별 점수' 줄(카메라, 렌즈와 센서, 빛과 공간, 몸과 총, 소리)이 있으면 CRITIC_LOG.md에 기준별 중앙값도 적는다. 답 형식이 바뀐 라운드는 CRITIC_LOG.md에 표시한다. 그 앞뒤의 전체 점수는 조건이 달라 그대로 견줄 수 없다.
- 모두 서로 다른 호출로 부른다. 넘겨주는 것은 파일 경로뿐이다. ab-judge에게는 자기 벌의 A/B 시트와 refs/ 폴더의 경로를 준다. critic에게는 비교 시트, 연속 프레임 묶음, out/perf.json, out/audio.json의 경로를 준다. 코드, 만든 과정, 이전 결과, 무엇을 고쳤는지는 넘기지 않는다.

## 우연을 조심한다
- 부호 검정은 갈린 쌍만 본다. 판정자를 늘려도 쌍의 수는 늘지 않는다. 우연의 폭은 갈린 쌍의 수가 정한다.
- 쌍끼리 완전히 독립은 아니다. 같은 장면에서 나온 정지 화면과 연속 프레임이 있다. p는 어림값이고, 세션이 통과해도 단계의 승인은 사람이 한다.
- 한 세션에서 끝 평가를 여러 번 돌리면 우연히 한 번 통과할 가능성이 쌓인다. 통과로 치는 것은 최종 빌드의 끝 평가다. 그 앞의 라운드에서 통과했어도 빌드를 바꿨다면 다시 받는다.
- 판정은 글자 B로 쏠리는 경향이 있다(지난 51라운드에서 표가 나온 판정의 61%). 좌우 교차가 이 쏠림이 승패에 들어가는 것을 막는다. 글자 집계는 매 라운드 함께 본다.

## 영점 확인
같은 빌드를 두 번 찍어 좌우 교차로 판정한다. A/B 도구나 판정자 지침을 고칠 때마다 다시 한다.

- 갈린 쌍이 5개 이상이면 치우침이 있다고 본다. 같은 빌드끼리이므로 두 벌에서 같은 쪽이 이기는 쌍은 거의 없어야 한다.
- 글자 집계의 양측 p가 0.01 아래면 글자 쏠림이 있다고 본다. 좌우 교차가 결과에 미치는 영향은 막아 주지만, 시트를 만드는 과정이 두 자리를 다르게 다룬다는 신호일 수 있다. 두 화면의 크기, 압축, 배치가 같은지 확인한다.
- `npm run ab -- score <라운드> ... --zero`가 이 두 기준으로 판정한다. 결과는 CRITIC_LOG.md에 적는다. 승, 패, 구분 안 됨, A와 B를 고른 수를 적는다.

## 세션 안에서의 순서
1. 시작: `npm run shots`, 기준선 저장, 비교 시트를 critic 3명에게. 결과를 CRITIC_LOG.md에 적는다. 지난 세션의 끝 평가 뒤로 빌드가 바뀌지 않았다면 critic 판정은 그 결과를 그대로 쓴다. 화면의 일부만 바꾸는 묶음이면 확대 영역을 PROGRESS.md에 적는다.
2. 중간: 작업 묶음의 큰 덩어리가 끝났을 때 `npm run shots`, A/B 시트 두 벌을 ab-judge 4명에게(벌마다 2명).
3. 끝: `npm run check`, `npm run perf`, `npm run shots`, A/B 시트 두 벌을 ab-judge 4명에게, 비교 시트를 critic 3명에게. 결과를 CRITIC_LOG.md에 적고 전후 시트를 만든다.

작은 수정마다 판정자를 부르지 않는다. 그 사이의 확인은 스크린샷을 직접 보는 것으로 한다.

## 통과하지 못했을 때
- 미달이면 기준선이 이긴 쌍과 방향이 갈린 쌍의 판정 근거, 판정자들의 '공통 격차'를 읽는다. 같은 수정을 더 쌓지 말고 접근을 바꾼다.
- 판정 불가(갈린 쌍이 5개 미만)면 실패가 아니다. 확대 쌍으로 다시 판정한다.
- 세 번 연속 제자리면 원인을 PROGRESS.md에 적는다. 판정이 흔들린 탓으로 보이면 영점 확인을 다시 한다.
- 점수나 승패가 나아지지 않는다는 이유로 마감하지 않는다. 마감은 통과 기준을 충족했을 때와 시간 상한이 지났을 때만 한다.

## 화면이 아닌 동작
봇의 전술, 반응, 난이도처럼 스크린샷으로 판정할 수 없는 것에는 A/B를 쓰지 않는다.
- 고치기 전에 문제를 재현하는 검사를 먼저 만든다. 시드를 고정한 자동 플레이로 상황을 만들고 수치로 판정한다. 예: 총성이 난 뒤 봇이 반응하기까지 걸린 시간, 엄폐물에 도달한 비율, 같은 자리에 끼어 있던 시간.
- 그 검사는 고치기 전에 실패하고 고친 뒤에 통과해야 한다. 통과한 검사는 `npm run check`에 넣어 다시 깨지지 않게 한다.
- 자동 플레이는 실제 입력 이벤트로 조작한다. 내부 상태를 직접 바꿔서 통과시키지 않는다.

## 증거
세션이 끝나면 docs/shots/<단계>/에 다음을 커밋한다.
- 전후 시트. 레퍼런스가 들어간 이미지는 커밋하지 않는다.
- 측정값 요약: check 결과, 프레임 시간, 소리 통계, A/B 승패와 부호 검정 p(옛 방식 비율은 참고로), 점수 중앙값, 식별 정답률.
- docs/verdicts/의 라운드별 판정 원문과 쌍별 결과.

0단계에서는 전후가 없으므로 빌드 화면만 모은 시트와 측정값 요약을 docs/shots/baseline/에 커밋한다.
