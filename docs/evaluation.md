# 평가 절차와 도구 요구사항

첫 빌드에서는 레퍼런스 없이 채점해서 점수가 1~2점씩 흔들렸다. 그 점수로는 방금 한 수정이 화면을 낫게 했는지 알 수 없었고, 점수가 제자리이거나 흔들린다는 이유로 두 번 마감했다. 이 문서는 그 문제를 고치는 절차다. docs/verification.md의 도구는 그대로 쓰고 아래를 더한다.

## 잣대는 두 가지다
- 전후 비교(A/B): 세션을 시작할 때의 빌드와 지금 빌드 중 어느 쪽이 실제 영상에 가까운가. 화면의 진척은 이것으로 판단한다. 같은 장면 둘을 나란히 놓고 고르는 판정은 한 장에 점수를 매기는 판정보다 덜 흔들린다.
- 레퍼런스와의 거리: 레퍼런스와 섞어 놓았을 때 빌드가 얼마나 가려지는가(식별 정답률), 몇 점인가(점수 중앙값). 추세를 보는 용도다. 세션의 통과 기준으로 쓰지 않는다.

## npm run ab
구현 방법과 인자 형식은 자유다. 아래 동작과 저장 위치만 지킨다.

- 기준선 저장: 지금 out/shots/의 스크린샷과 연속 프레임 묶음을 out/baseline/<이름>/에 복사한다. `npm run shots`는 out/shots/를 매번 비우므로, 세션을 시작하면 수정하기 전에 먼저 저장한다.
- 시트 만들기: 기준선과 현재 out/shots/에서 같은 이름의 장면끼리 쌍을 짓는다. 쌍마다 번호를 붙이고, 두 화면에 A와 B를 무작위로 배정해 나란히 놓는다. 시트는 out/ab/round-N.png에 저장하고, 어느 쪽이 새 빌드인지는 out/keys/ab-round-N.json에만 적는다.
- 연속 프레임 묶음도 같은 방식으로 쌍을 짓는다. 쌍은 모두 15개 이상으로 둔다. 지금 `npm run shots`가 찍는 정지 화면 15장과 연속 프레임 4묶음, 모두 19쌍이다.
- 정지 화면 가운데 4장(`12-close-…` ~ `15-close-…`)은 1~2 m 안의 표면과 손과 총을 찍은 가까운 장면이다. 2026-11-14에 사용자의 결정으로 더했다. 판정 시트의 한 칸(약 656×369)에서는 모서리 닳음, 표면 요철, 총의 세부처럼 몇 화소짜리 변화가 보이지 않아서다. 가까운 장면은 A/B에만 쓰고 `npm run sheet`의 레퍼런스 비교에는 넣지 않는다(식별 정답률과 점수를 이전 라운드와 같은 구성으로 보기 위해서다).
- 두 화면은 같은 크기와 같은 압축을 거친다. 파일 이름, 테두리, 해상도, 배치 순서로 어느 쪽이 새 빌드인지 드러나면 안 된다.
- 판정용 이미지가 크면 판정자가 읽을 때 축소되어 세부가 사라질 수 있다. 시트 한 장에는 쌍을 서너 개만 넣고 여러 장으로 나눈다. 비교 시트도 칸이 많으면 나눈다.
- 채점: 라운드 번호와 판정 목록을 받아 정답 키와 대조하고, 새 빌드를 고른 비율만 출력한다. '구분 안 됨'은 반으로 센다. 키 내용은 출력하지 않는다. 판정을 여러 벌 받으면 벌마다의 비율, 합친 비율, 쌍별 다수결로 센 비율을 함께 출력한다.
- 전후 시트: 판정용 시트와 별개로, 왼쪽이 기준선이고 오른쪽이 새 빌드인 시트를 만든다. 사람이 보는 용도다. docs/shots/ 아래에 JPEG로 저장해 파일을 작게 유지한다.
- 폴더 만들기와 파일 복사는 스크립트 안에서 처리한다. 허용 목록에 없는 셸 명령을 쓰면 권한 확인에서 작업이 멈출 수 있다.

## 판정자
- ab-judge: A/B 시트를 보고 쌍마다 A, B, 구분 안 됨 중 하나로 답한다.
- critic: 레퍼런스와 섞은 비교 시트를 보고 칸마다 빌드인지 판정하고 0~10점으로 채점한다.
- 평가할 때마다 각각 3번씩, 서로 다른 호출로 부른다. 점수는 세 값의 중앙값을 쓴다.
- 넘겨주는 것은 파일 경로뿐이다. ab-judge에게는 A/B 시트와 refs/ 폴더의 경로를 준다. critic에게는 비교 시트, 연속 프레임 묶음, out/perf.json, out/audio.json의 경로를 준다. 코드, 만든 과정, 이전 결과, 무엇을 고쳤는지는 넘기지 않는다.

## 우연을 조심한다
판정자 세 명은 같은 그림을 본다. 판정 수를 셋으로 늘려도 우연의 폭은 쌍의 수가 정한다. 쌍 15개에서 두 빌드에 차이가 없어도 11쌍 이상이 새 빌드 쪽으로 기울 확률은 약 6%다. 그래서 통과 여부는 쌍별 다수결로 센 비율로 판단하고, 쌍을 15개 아래로 줄이지 않는다.

## 영점 확인
A/B 도구를 만들거나 고친 뒤에는 같은 빌드를 두 번 찍어 서로 비교한다. 같은 빌드끼리이므로 대부분 '구분 안 됨'이 나와야 한다. 쌍별 다수결로 한쪽이 쌍의 80% 이상(15쌍이면 12쌍, 19쌍이면 16쌍)이면 시트나 판정 방식에 치우침이 있다고 본다. 원인을 찾아 고친 뒤에 쓴다. 결과는 CRITIC_LOG.md에 적는다.

## 세션 안에서의 순서
1. 시작: `npm run shots`, 기준선 저장, 비교 시트를 critic 3명에게. 결과를 CRITIC_LOG.md에 적는다. 지난 세션의 끝 평가 뒤로 빌드가 바뀌지 않았다면 critic 판정은 그 결과를 그대로 쓴다.
2. 중간: 작업 묶음의 큰 덩어리가 끝났을 때 `npm run shots`, A/B 시트를 ab-judge 3명에게.
3. 끝: `npm run check`, `npm run perf`, `npm run shots`, A/B 시트를 ab-judge 3명에게, 비교 시트를 critic 3명에게. 결과를 CRITIC_LOG.md에 적고 전후 시트를 만든다.

작은 수정마다 판정자를 부르지 않는다. 그 사이의 확인은 스크린샷을 직접 보는 것으로 한다.

## 통과하지 못했을 때
- 선호 비율이 통과 기준에 못 미치면 판정 근거와 '공통 격차'를 읽는다. 같은 수정을 더 쌓지 말고 접근을 바꾼다.
- 세 번 연속 제자리면 원인을 PROGRESS.md에 적는다. 판정이 흔들린 탓으로 보이면 영점 확인을 다시 한다.
- 점수나 비율이 오르지 않는다는 이유로 마감하지 않는다. 마감은 통과 기준을 충족했을 때와 시간 상한이 지났을 때만 한다.

## 화면이 아닌 동작
봇의 전술, 반응, 난이도처럼 스크린샷으로 판정할 수 없는 것에는 A/B를 쓰지 않는다.
- 고치기 전에 문제를 재현하는 검사를 먼저 만든다. 시드를 고정한 자동 플레이로 상황을 만들고 수치로 판정한다. 예: 총성이 난 뒤 봇이 반응하기까지 걸린 시간, 엄폐물에 도달한 비율, 같은 자리에 끼어 있던 시간.
- 그 검사는 고치기 전에 실패하고 고친 뒤에 통과해야 한다. 통과한 검사는 `npm run check`에 넣어 다시 깨지지 않게 한다.
- 자동 플레이는 실제 입력 이벤트로 조작한다. 내부 상태를 직접 바꿔서 통과시키지 않는다.

## 증거
세션이 끝나면 docs/shots/<단계>/에 다음을 커밋한다.
- 전후 시트. 레퍼런스가 들어간 이미지는 커밋하지 않는다.
- 측정값 요약: check 결과, 프레임 시간, 소리 통계, A/B 선호 비율, 점수 중앙값, 식별 정답률.

0단계에서는 전후가 없으므로 빌드 화면만 모은 시트와 측정값 요약을 docs/shots/baseline/에 커밋한다.
